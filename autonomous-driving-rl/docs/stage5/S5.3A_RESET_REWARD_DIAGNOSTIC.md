# S5.3A follow-up: reset progress and training visibility

## Finding

`Stage5TrainingEnv.reset()` receives the simulator's initial `route_completion`, but the adapter previously initialized its previous-progress value to `0.0`. The first reward calculation therefore treated the route progress already present at spawn as progress made by the policy. This is a small reward-accounting defect; it does not change the observation, action, Platform V1 evaluation metrics, or the frozen reward specification.

The adapter now initializes both previous and maximum progress from the reset info. A real MetaDrive regression test uses a geometry with a non-zero reset offset and verifies that the first progress reward equals only the route-completion change after the action.

## What the pilot logs now show

The pilot callback writes `checkpoints/training_steps.jsonl` and `checkpoints/training_action_summary.json` in each run directory. The step log records geometry identity, episode step, action, speed, route completion, reward components, and terminal outcome. This allows the next run to show whether the stochastic training policy is applying throttle, braking, or staying near zero while it explores.

To inspect a frozen checkpoint visually, run from `autonomous-driving-rl/`:

```powershell
python scripts/watch_stage5_sac_checkpoint.py `
  --checkpoint runs/stage5_pilot/<run-id>/checkpoints/step_10000 `
  --split results/stage5/pilot_split_v1.json
```

The viewer runs deterministic inference in a separate simulator process, uses only the fixed internal TRAIN diagnostic split, and does not update weights or training state.

## Historical result status

The already completed S5.3A run and its report/checkpoints remain unchanged. That run predates the reset-accounting fix, so its cumulative reward includes the reset offset described above. Its measured route completion, success/safety outcomes, and action behavior remain measurements from that historical run.
